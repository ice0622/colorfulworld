# Lessons

## 検証用に2つ目の dev サーバを同じ `.next` で起動しない（2026-06-18）

**ミス**: OG画像の修正を検証するため `next dev -p 3001`（webpack）を起動した。
ユーザーは既に `next dev --turbopack`（3000）を動かしており、両者が同じ `.next/` を
上書きし合って turbopack のランタイムチャンク（`chunks/ssr/[turbopack]_runtime.js`）が消え、
ユーザー側で `Cannot find module ... [turbopack]_runtime.js` のランタイムエラーが発生した。

**原因**: 同一プロジェクトの `.next` は1プロセス専有。bundler（turbopack/webpack）が違うと特に壊れる。

**今後のルール**:
- 検証で dev/build を回す前に必ず `ps aux | grep next` で既存プロセスを確認する。
- 既に dev が動いていれば、新規起動せずそれを使う（署名付きURLを叩くだけなら既存サーバでよい）。
- どうしても別プロセスが必要なら、git worktree など `.next` を共有しない隔離環境で行う。
- 本番ビルド検証（`next build`）も `.next` を書くので、ユーザーの dev が動作中は実行しない。
  実行するならユーザーに dev 停止を依頼してから。

## 【再発】ユーザーの dev 稼働中に `next build` を実行して `.next` を上書き（2026-06-24）

**ミス**: 画像最適化の検証で `npm run build` と `npm run start` を実行したが、ユーザーが
`next dev --turbopack`（:3000）を稼働中だった。レッスン#1で文書化済みの失敗を**繰り返した**。
原因は2つ:
1. **セッション開始時に lessons をレビューしなかった**（CLAUDE.md のルール違反）。
2. ビルド前に `ps aux | grep next` を実行しなかった。`:3100` で別ポート起動すれば安全と
   誤認したが、`next build` / `next start` は**ポートに関係なく同じ `.next/` を共有**するため無意味。

**今後のルール（強化）**:
- **セッション開始時、コードを触る前に `tasks/lessons.md` を必ず一読する**（プロジェクト方針）。
- `next build` / `next start` / `next dev` を打つ**直前に毎回** `ps aux | grep next` を実行する。
  別ポートは免罪符にならない（`.next` 共有）。
- ユーザーの dev が動いていたら: ①検証はそのサーバ（:3000）に curl で当てる、②`.next` を書く操作
  （build/start）が必要なら **git worktree で隔離**するか、**ユーザーに dev 停止を依頼**してから。
- `next/image` の最適化エンドポイント検証は、ユーザーの dev サーバ（:3000）に
  `/_next/image?url=...&w=...&q=...` を直接 curl すれば足り、別サーバ起動は不要だった。

## ホバー拡大とワンショットアニメの定番バグ（2026-06-19）

**ミス**: いいねボタン刷新で3点指摘を受けた。
1. `hover:scale-[1.02]` でホバーを外したときに「ちらつき」。要素が拡大すると境界で
   カーソルのホバー判定が拡大↔縮小を往復し点滅する典型パターン。
2. タップ時の `+1` が「出たり出なかったり」。`pulse` を 600ms で true→false する方式だと、
   true の最中に連打しても要素が再マウントされずCSSアニメが再生されない＋前のタイマーが途中で消す。
3. 不要なラベル（「あなた」）を付けていた。説明過多。

**今後のルール**:
- インタラクティブ要素に **hover で transform:scale を掛けない**（押下=`active:scale` はOK）。
  どうしても拡大したいなら内側ラッパに掛ける／`transform-gpu` で層を固定し、境界往復を避ける。
- **ワンショットの再生アニメは「フラグのトグル」でなく「key の更新で再マウント」**して毎回やり直す。
  連打対応では既存タイマーを `clearTimeout` してから貼り直す。
- ラベルは最小限。UIで自明なものに説明テキストを足さない（ミニマル方針）。

## 自サイトのレイアウト「モック」は Artifact でなく実サイトに作る（2026-06-26）

**ミス**: 「サムネをヒーロー表示にしたい、一回モックを作ってみよう」に対し、claude.ai の
Artifact（HTML）で3案の比較モックを作った。ユーザーの反応は「普通にサイトに埋め込みでよかったのに」。
動いている自分の Next.js サイトがあるのに、わざわざ外部の使い捨て HTML を作って二度手間にした。

**原因**: 「モック＝外部で素早く可視化」と短絡した。実プロジェクトでは、実コンポーネント・実トークン・
実データで動くものを直接いじる方が、確認も微調整も速い（ユーザーは自分でブラウザで見て調整できる）。

**今後のルール**:
- **稼働中の自サイトに対する「モック/試作」依頼は、原則その場で実コードに実装する**（feature ブランチ or
  条件分岐で出し分け）。Artifact 化は「コードに触れない / 共有用の静的比較 / 環境が無い」ときだけ。
- 複数案を見せたいなら、実サイト側にトグルや一時的な分岐を置いて切り替えられるようにする方が、
  デザインシステムの忠実度が高く本実装への移行もゼロコスト。
- 関連: [[feedback_autonomous_until_user_gate]]（手が止まる所まで実装で進める）の精神と同じ。

## 「実体のデータソース」を確認せず死にコードを編集しかけた（2026-06-29）

**ミス**: 写真記事のSEO改善で、`content/posts/France.md` の frontmatter や本文を直接編集する前提で
計画・着手した。実際には `content/posts/*.md` は **死にコード**（`hasDb` フォールバック路）で、
本番の記事は **Postgres(Neon) + 自作CMS**（`src/app/(admin)/admin/`）で管理されていた。
ユーザーに「それ死にコードです。CMS移行済みで実体は別の場所」と指摘されて初めて気づいた。

**原因**: ファイルが存在し中身も最新に見えたので「ここが記事の実体」と短絡した。
`hasDb ? DB : markdown` の二系統（`src/lib/content.ts`）を読んでいたのに、
**どちらが本番で生きているか**を確認しなかった。デュアルモード/フォールバック実装では
「コードが存在する＝使われている」ではない。

**今後のルール**:
- **編集対象が本番で実際に通る経路か、着手前に確認する**。特に「DB or ファイル」「旧 or 新」の
  二系統がある実装では、`hasDb`・環境変数・フィーチャーフラグの分岐を読み、生きている側を特定する。
- 移行途中のリポジトリでは、ファイルの存在・新しさを「現役」の証拠にしない。
  迷ったら「これ本番で使われてますか？」と早めに一次情報を取りに行く。
- 関連: このプロジェクトの記事の実体は CMS(DB)。詳細は記憶 [[project_colorfulworld_live_cms]] に集約。
