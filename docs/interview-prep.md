```
ユーザーのブラウザ
      ↓ HTTPS
  Vercel（ホスティング）
      ↓
  Next.js アプリ（App Router）
   ├── サーバーコンポーネント（SEO・初期表示担当）
   ├── クライアントコンポーネント（アニメーション・ボタン等）

         ├── Wisp CMS ─── ブログ記事のデータ
         └── Upstash Redis ─── いいね数の永続化
```

## 💬 面接Q&A 集

---

### Q1. このポートフォリオサイトについて教えてください

**回答例：**
> Next.js 15のApp Routerで作ったブログ型ポートフォリオサイトです。
> トップページには3Dの地球儀があって、訪問した国のマーカーをクリックするとその旅の記事に飛べる仕組みになっています。
> 記事データはWisp CMSというヘッドレスCMSで管理していて、デプロイはVercelの無料プランを使っています。
> いいねボタンのカウントだけUpstash Redisというサーバーレスなキーバリューストアで永続化しています。
> とにかく「維持コスト0円・自由度最大」を目標に設計しました。

**補足ポイント（深掘りされたとき用）：**
- 維持コスト0円：Vercel無料枠 + Upstashの無料枠 + Wisp CMSの無料枠で全部賄えている
- 自分でサーバーを立てる必要なし = サーバーレスアーキテクチャの実践

---

### Q2. Next.js を選んだ理由は？

**回答例：**
> 主にSEOとパフォーマンスの面でReact単体より優れているからです。
> ブログ記事のページはサーバーコンポーネントで作っているので、記事本文がHTMLとして配信されSearch Engineにインデックスされやすい状態になっています。
> また、App RouterのファイルベースルーティングはURL設計がシンプルで、例えば `/blog/[slug]` というフォルダ名がそのままURLの動的パラメータになります。
> Next.js 15からはTurbopackが標準になったので開発中のビルドも体感で速くなりました。

---

### Q3. サーバーコンポーネントとクライアントコンポーネントの使い分けを教えてください

**回答例：**
> 「インタラクションが必要かどうか」で分けています。
>  
> **サーバーコンポーネント**（`async`関数、デフォルト）：
> - ブログ記事ページ（`/blog/[slug]/page.tsx`）
> - CMSからデータをfetchして最初からHTMLに含める → SEOに有利
> - `generateMetadata` でOGPタグも動的に生成できる
>  
> **クライアントコンポーネント**（ファイル先頭に `"use client"` と書く）：
> - `Globe.tsx`（3Dグローブ、`useEffect`でcanvas描画）
> - `LikeButton.tsx`（クリックイベント・state管理）
> - `CommentSection.tsx`（TanStack Queryでのインタラクティブfetch）
>  
> 混在させるときは、サーバーコンポーネントの**子として**クライアントコンポーネントを渡す形を取っています。

---

### Q4. ヘッドレスCMSとは何ですか？なぜ使ったのですか？

**回答例：**
> 従来のCMS（WordPressなど）は「管理画面 + データ + 表示テンプレート」がセットですが、
> ヘッドレスCMSは「データの保存・管理だけ」に特化していて、表示側（フロントエンド）は完全に自由に作れます。
>  
> このサイトではWisp CMSを使っています。
> フロントエンドからは `@wisp-cms/client` というSDKで記事を取得するだけなので、コードとしては：
> ```typescript
> const result = await wisp.getPost(slug);  // 記事1件取得
> const { posts } = await wisp.getRelatedPosts({ slug, limit: 3 });  // 関連記事
> ```
> これだけで記事データが取れます。
> デザインや機能は100%自分でコントロールできるため、WordPressのように「テンプレートの都合に縛られる」ことがないのが採用理由です。

---

### Q5. いいねボタンのしくみを教えてください

**回答例：**
> フロントエンドとバックエンドAPIに分かれています。
>  
> **フロントエンド（`LikeButton.tsx`）：**
> - ボタンをクリックすると即座にUI上のカウントを1増やす（楽観的UI更新）
> - 同時にバックエンドの `/api/like` にPOSTリクエストを送る
> - 1人が連打できる上限は10回まで（`MAX_MY_LIKES = 10`）
> - `localStorage` にクライアントIDを保存して匿名識別している
>  
> **バックエンドAPI（`/api/like/route.ts`）：**
> - Next.jsのRoute HandlerとしてVercel上で動くサーバーレス関数
> - Upstash Redis（HTTPで使えるサーバーレスRedis）にいいね数をRedis Hashで保存
> - `redis.hincrby(key, "count", 1)` でアトミックにインクリメント
> - IPアドレスベースのレート制限も実装（10秒間に50回まで）
>  
> **なぜRedisか？**
> ファイルや環境変数に保存すると、Vercelの環境では複数インスタンスに分散しているため数値がずれます。
> Redisなら単一の真のデータストアとして機能するため、正確な集計ができます。

### Q6. 動的OG画像の生成とは何ですか？

**回答例：**
> SNSでリンクをシェアしたときに出てくるプレビュー画像（OGP画像）を、
> ブログ記事ごとに自動生成する仕組みです。
>  
> `/api/og-image` というRoute Handlerが画像生成APIになっていて、
> クエリパラメータにタイトルを渡すとその文字が入った画像をPNGで返します。
>  
> セキュリティとして**署名検証**も入っています。
> HMAC署名を使って「正規のパラメータかどうか」チェックしているため、
> 外部から任意のテキストで画像を生成されることを防いでいます（`verifyOgImageSignature`）。

### Q7. パフォーマンスやSEOで工夫したことはありますか？

**回答例：**
> いくつかあります：
>  
> **SEO：**
> - `generateMetadata` で記事ごとに動的にタイトル・説明・OGP画像を生成
> - Blog記事ページに **JSON-LD**（構造化データ）を埋め込み、Googleに `BlogPosting` として認識させている
> - RSSフィードも `/rss` エンドポイントで自動生成
> - Googleサーチコンソール用の `meta` タグをlayout.tsxに追加
>  
> **パフォーマンス：**
> - サーバーコンポーネントで初期表示のJavaScript量を削減
> - 3DグローブはSSRできないためDynamic Import（`next/dynamic`）でクライアントのみロード
> - Vercel Speed InsightsでCore Web Vitalsをリアルタイムで監視
> - `next/font` でフォントの最適化（レイアウトシフト防止）

### Q8. TypeScriptをなぜ使っていますか？

**回答例：**
> 「コードを書いている途中」にバグを発見できるからです。
> 例えばAPIのレスポンス型が変わったとき、TypeScriptがあれば使っている全箇所で即座にエラーが出ます。
> JavaScriptだと実行してみるまで気づけないことが多い。
>  
> このサイトでは特にWisp SDKの型定義、ZodでのAPIバリデーション、schema-dtsライブラリを使ったJSON-LDの型安全な記述など、型の恩恵を受けている箇所が多くあります。

---

### Q9. ダークモードはどう実装していますか？

**回答例：**
> `next-themes` というライブラリを使っています。
> `Providers` コンポーネントで `<ThemeProvider>` をラップしており、
> `defaultTheme="system"` にすることでOSの設定（ライト/ダーク）に自動追従します。
>  
> `"use client"` を書く必要があるThemeProviderは、`next/dynamic` でSSRを無効化してimportしています（ハイドレーションのフラッシュ防止）。
> Tailwind CSSの `dark:` プレフィックスで各コンポーネントのダーク配色を定義しています。

## 🔑 覚えておきたい用語まとめ

| 用語 | 一言説明 |
|---|---|
| **App Router** | Next.js 13+のルーティング方式。`app/`フォルダ以下のファイルがURLになる |
| **サーバーコンポーネント** | サーバー側でHTMLを生成するReactコンポーネント。SEO・初期表示に有利 |
| **クライアントコンポーネント** | ブラウザでJSが動くコンポーネント。`"use client"`で宣言 |
| **Route Handler** | `route.ts`ファイルで作るAPIエンドポイント（旧APIRoutes相当） |
| **ヘッドレスCMS** | フロントから独立したデータ管理API。今回はWisp CMS |
| **Upstash Redis** | HTTPで使えるサーバーレスRedis。Vercel上でも使える |
| **OGP** | SNSシェア時のプレビュー情報。`<meta property="og:title">`等 |
| **JSON-LD** | Googleが読む構造化データ。`<script type="application/ld+json">` |
| **TanStack Query** | サーバーデータのfetch・キャッシュ・再取得を管理するClienライブラリ |
| **Zod** | TypeScriptでスキーマ定義 + バリデーションをする型安全ライブラリ |
| **shadcn/ui** | Radix UIベースのコンポーネント集。コードをコピーして使うスタイル |
| **cobe** | WebGL（canvas）で3Dグローブを描画するライブラリ |
| **サーバーレス** | サーバーを自分で管理しない。関数単位でクラウドが実行してくれる方式 |

## ⚡ 深掘り質問への備え（1行回答）

- **「なぜVercelですか？」** → Next.jsの開発元なので統合がシームレス。無料でもCI/CD・プレビューURL・エッジ配信が揃っている
- **「Dockerは使っていないんですか？」** → 開発環境（このDockerコンテナ）と本番（Vercel）を分けている。本番はVercel側でコンテナを管理してくれる
- **「テストはどうですか？」** → 現状は手動確認のみ。Jest + React Testing Libraryを導入したいと思っている（正直に言う）
- **「セキュリティ面で意識したことは？」** → OG画像APIにHMAC署名検証、Redisへのアクセスにレート制限（IP別に10秒50リクエスト上限）、`sanitize-html`でコメントのXSS対策
- **「CI/CDはどうなっていますか？」** → GitHubにpushするとVercelが自動でbuildしてデプロイする。PRを出すとプレビューURLも自動作成される
